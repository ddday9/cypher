# Установка: сервер на Linux, клиент на Windows

## Что понадобится

* Linux-ВМ с публичным IP, на которой свободен порт 443.
* Домен (подойдёт любой дешёвый) с A-записью на IP ВМ.
* Go 1.26+ для сборки (более старый Go сам скачает нужную версию) (или готовые бинарники из `make linux windows`).

## 1. Сборка

На любой машине с Go:

```bash
make linux windows
```

Получатся `bin/cypher-linux-amd64` и `bin/cypher-windows-amd64.exe`.

## 2. Сервер (Linux)

**Рекомендуемый способ — Docker:** см. [docker.md](docker.md). Ниже —
установка без Docker, как служба systemd.

### Быстро: скрипт

Скопируйте на сервер бинарник и папку `deploy/` (например, `scp -r bin deploy user@server:`),
затем на сервере:

```bash
sudo ./deploy/install-server.sh --domain example.com --email you@example.com
```

Скрипт:
* создаёт системного пользователя `cypher` и `/etc/cypher`;
* получает сертификат Let's Encrypt (на время получения нужен свободный порт 80)
  и ставит hook, который после каждого продления копирует сертификат в
  `/etc/cypher/` с правами для `cypher` — сервер подхватывает его сам;
* генерирует ключ, пишет `/etc/cypher/server.json`;
* кладёт сайт-прикрытие в `/var/www/cypher` (свой сайт: `--site ./my-site`);
* ставит и запускает systemd-службу, открывает порт в `ufw`, если он включён;
* печатает готовый блок `outbound` для клиента с ключом.

Без домена, для проверки: `--self-signed` (сертификат на IP сервера;
`/etc/cypher/cert.pem` нужно скопировать на клиент и указать в `"ca"`).

Добавить ещё одного пользователя (отдельный ключ, например для телефона):

```bash
sudo ./deploy/install-server.sh --add-user phone
```

Повторный запуск обновляет бинарник и службу, существующий конфиг не трогает.

### Проверка с другого Linux-хоста

```bash
./deploy/test-client.sh --server example.com:443 --key КЛЮЧ
```

Скрипт поднимает временный клиент и проверяет: сайт-прикрытие отдаётся без
ключа; TCP через туннель работает и выходит с IP сервера; UDP (DNS-запрос к
1.1.1.1) проходит через туннель.

Логи сервера:

```bash
journalctl -u cypher -f
```

## 3. Клиент (Windows)

1. Создайте папку, например `C:\cypher`, положите туда
   `cypher-windows-amd64.exe` (можно переименовать в `cypher.exe`).
2. Скачайте `geosite.dat` и `geoip.dat` — те же, что для Xray, например из
   [Loyalsoldier/v2ray-rules-dat](https://github.com/Loyalsoldier/v2ray-rules-dat/releases)
   или [runetfreedom/russia-v2ray-rules-dat](https://github.com/runetfreedom/russia-v2ray-rules-dat/releases),
   и положите рядом.
3. Скопируйте `examples/client.json` в `C:\cypher\client.json`, впишите
   `server` (`example.com:443`) и тот же `key`, что на сервере.
4. Проверьте конфиг и запустите:

```bash
cypher.exe check -c client.json
```

```bash
cypher.exe run -c client.json
```

5. Включите прокси в Windows: **Параметры → Сеть и Интернет → Прокси-сервер →
   Использовать прокси-сервер**, адрес `127.0.0.1`, порт `10809` (HTTP).
   Либо укажите SOCKS5 `127.0.0.1:10808` в настройках браузера или программы.

Так через прокси идут программы, которые используют системный прокси
(браузеры и большинство приложений). Чтобы пустить через cypher вообще весь
трафик системы, включая игры и UDP, используйте режим TUN.

### Режим TUN (весь трафик Windows)

1. Скачайте Wintun с https://www.wintun.net, возьмите из архива
   `wintun\bin\amd64\wintun.dll` и положите рядом с `cypher.exe`.
2. Возьмите за основу `examples/client-tun.json`.
3. Запустите **от администратора** (PowerShell или cmd «Запуск от имени
   администратора»):

```bash
cypher.exe run -c client-tun.json
```

Системный прокси в Windows при этом не нужен. Остановка — Ctrl+C: адаптер,
маршруты и DNS удаляются вместе с ним.

Что происходит:
* создаётся адаптер `cypher`, в него направляются маршруты `0.0.0.0/1` и
  `128.0.0.0/1` (и IPv6). Основной маршрут не трогается — после выхода сеть
  остаётся как была. Локальная сеть (192.168.x.x и т. п.) идёт мимо TUN;
* собственные соединения cypher (к серверу и `direct`) привязываются к
  физическому интерфейсу, поэтому не зацикливаются. Смена Wi-Fi ↔ кабель
  отслеживается автоматически;
* адрес сервера резолвится один раз при старте;
* **DNS**: адаптеру назначается DNS-сервер внутри TUN, все DNS-запросы
  (порт 53 на любой адрес) перехватываются и уходят на `dnsHijack`
  (по умолчанию 1.1.1.1) по правилам маршрутизации — обычно через туннель,
  провайдер их не видит;
* **sniff**: приложения подключаются по IP, поэтому домен для правил
  `geosite:` берётся из SNI (TLS) или заголовка Host (HTTP).

Ограничения режима TUN:
* ICMP (ping) через TUN не проходит;
* Windows иногда параллельно спрашивает DNS и у физического адаптера
  («smart multi-homed name resolution»). Если важно полностью исключить
  такие утечки, отключите эту функцию групповой политикой: «Конфигурация
  компьютера → Административные шаблоны → Сеть → DNS-клиент → Отключить
  интеллектуальное разрешение многоадресных имён»;
* домен для правил берётся только из TCP (TLS/HTTP). QUIC (UDP) маршрутизируется
  по IP.

На Linux режим TUN работает так же (нужен root или `CAP_NET_ADMIN`); если есть
systemd-resolved, cypher направляет все DNS-запросы в TUN через `resolvectl`.

## Маршрутизация

Синтаксис совместим с Xray:

| Поле | Значения |
|---|---|
| `domain` | `geosite:google`, `geosite:google@cn` (атрибут), `domain:example.com` (домен и поддомены), `full:www.example.com`, `keyword:goog`, `regexp:^ads\d+\.`, строка без префикса = keyword |
| `ip` | `geoip:ru`, `geoip:private`, `geoip:!ru` (всё, кроме), `10.0.0.0/8`, `1.2.3.4` |
| `port` | `443`, `"1000-2000"`, `"80,443,8000-9000"` |
| `network` | `tcp`, `udp`, `tcp,udp` |
| `inboundTag` | `["socks"]` |

Внутри поля условия объединяются через ИЛИ, поля между собой — через И.
Правила проверяются по порядку; первое совпавшее определяет `outbound`. Если
ничего не совпало — `routing.default` (или первый outbound).

`domainStrategy`:
* `AsIs` (по умолчанию) — IP-правила применяются только к соединениям по IP.
* `IPIfNonMatch` — если домен не совпал ни с одним правилом, клиент резолвит
  его и проверяет IP-правила (например, `geoip:ru`). **Внимание:** это
  локальный DNS-запрос к провайдеру, он раскрывает домен.

## Обновление правил без перезапуска

Клиент каждые 3 секунды проверяет `geosite.dat`, `geoip.dat` и свой конфиг.
Если файл изменился (и не меняется ещё одну проверку, то есть уже докачан),
правила маршрутизации пересобираются и подменяются на лету. Открытые
соединения не рвутся.

* Если новый файл битый или правило ссылается на несуществующий outbound,
  в лог пишется ошибка, и продолжают действовать старые правила.
* На лету меняется только секция `routing`. Изменения `inbounds` и
  `outbounds` требуют перезапуска.
