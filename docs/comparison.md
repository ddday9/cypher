# cypher и Xray: чем отличаемся и что делать дальше

Документ честно сравнивает cypher с Xray-core (VLESS, REALITY, Vision,
XHTTP) и разбирает, как блокируют в России в 2025–2026 годах. Вывод в
конце: что добавить, чтобы cypher был не «ещё одним Xray», а устойчивее его.

## Коротко

* **Где cypher лучше Xray:** одноразовая аутентификация вместо постоянного
  UUID, нарезка и паддинг начала *каждого* потока, ротация соединений «как у
  браузера», встроенный сайт-прикрытие за nginx, свой Let's Encrypt без
  certbot, пользователи без перезапуска, правила по приложениям, перечитывание
  баз и правил на лету, клиент для Windows «из коробки».
* **Где cypher такой же:** снаружи это TLS 1.3 к собственному домену с
  браузерным отпечатком — то же, что VLESS+TLS/Trojan. По форме трафика
  после рукопожатия мы ближе к VLESS+Vision, чем к чему-то принципиально
  новому.
* **Где cypher хуже:** нет REALITY (нужен свой домен), нет транспортов поверх
  HTTP (XHTTP/gRPC) и через CDN, нет UDP-транспорта, меньше проверен
  временем.
* **С версии 0.2:** заморозка соединений распознаётся за секунды, а режим
  «против заморозки» переносит сессию короткими соединениями ниже порога —
  этого у Xray в таком виде нет (ближе всего XHTTP packet-up).
* **Главное:** самый массовый метод ТСПУ 2025–2026 — «заморозка» TCP после
  ~16 КБ к зарубежным хостингам и белые списки IP на мобильных сетях — бьёт
  по cypher так же, как по Xray. Это не исправить паддингом или отпечатком:
  нужны другие механизмы (раздел «Что добавить»).

## Сравнение по функциям

| | Xray (VLESS + REALITY/TLS + Vision/XHTTP) | cypher |
|---|---|---|
| Внешний вид | TLS 1.3; REALITY — чужой домен без своего сертификата | TLS 1.3 к своему домену, настоящий сертификат Let's Encrypt |
| Отпечаток ClientHello | uTLS (fingerprint) | uTLS: Firefox по умолчанию, Chrome, Safari, Edge, iOS, случайный из настоящих |
| Аутентификация | UUID внутри TLS, одинаковый в каждом соединении; REALITY — ключ в ClientHello | HMAC-SHA256 с меткой времени и nonce, каждый раз новый; защита от повтора |
| Активное зондирование | REALITY проксирует к чужому сайту; VLESS+TLS — fallback, обычно на nginx | сайт-прикрытие за nginx (HTTP/1.1 и HTTP/2), порт 80 — редирект как у обычного сайта |
| TLS-in-TLS | Vision: паддинг рукопожатия, затем внутренний TLS «как есть» | паддинг и нарезка первых кадров каждого потока, а не только первого |
| Мультиплексирование | mux.cool / XMUX (опционально) | smux всегда, пул из нескольких соединений |
| Поведение соединений | одно соединение на каждое подключение (без mux) | ротация по случайному времени и объёму, закрытие в простое |
| Транспорты | TCP, WebSocket, gRPC, HTTPUpgrade, XHTTP, QUIC/Hysteria (в форках) | только TCP+TLS |
| Через CDN | да (WS, gRPC, XHTTP) | нет |
| UDP | да | да (внутри туннеля), SOCKS5 UDP, TUN |
| Маршрутизация | geosite/geoip, домены, IP, порты, процессы (в клиентах) | то же, совместимо по формату; плюс `process` в ядре |
| Правила на сервере | да | да (`direct`/`block`, по пользователю) |
| Обновление баз и правил | перезапуск (в клиентах — обёртки) | на лету, встроенный таймер, без cron |
| Пользователи | правка конфига + перезапуск (или API) | `cypher user add/revoke`, без перезапуска, отзыв рвёт сессии |
| Сертификат | вручную / certbot / acme.sh | встроенный ACME (HTTP-01 через nginx и TLS-ALPN-01), автопродление на лету |
| Клиенты | v2rayN, Hiddify, NekoBox, Happ и др. | свой nevio для Windows, консольный для Linux/Windows |
| Зрелость | годы в бою против GFW и ТСПУ | новый код, не проверен в реальной сети с ТСПУ |

## Что делает ТСПУ (2025–2026)

Ниже — что известно из открытых источников. Многое — наблюдения
пользователей, а не замеры; уровень уверенности указан.

1. **Заморозка после ~16 КБ к зарубежным хостингам** (замерено несколькими
   участниками). Если TCP-соединение (TLS 1.2/1.3 и даже без TLS) идёт к IP
   крупного зарубежного хостинга (Hetzner, DigitalOcean, OVH, Cloudflare и
   др.), то после примерно 25 пакетов в одну сторону (≈ 15–20 КБ от сервера)
   пакеты перестают доходить. RST нет — клиент просто ждёт таймаута. Сильнее
   всего на мобильных операторах. Дробление пакетов не помогает: считаются
   байты соединения. Помогает только много коротких соединений — медленно и
   заметно. SSH и RDP, по наблюдению автора, не ограничивались.
   [net4people #490]
2. **Белые списки на мобильных сетях** (замерено пользователями). Сначала
   список по SNI (REALITY с SNI из белого списка работал), затем — по IP:
   на «чужие» IP не проходит даже ClientHello, работают только адреса из
   списка (крупные российские сервисы и их облака). SNI из списка с IP не из
   списка помогает «50 на 50» в зависимости от региона. Облачные VPS с
   «белыми» IP работали, пока в январе 2026 не потребовали разделить пулы
   адресов. [net4people #516; новости]
3. **Поведенческий анализ VLESS** (со слов авторов статей, часть — гипотезы).
   В конце 2025 года обновление ТСПУ начало ломать VLESS; в мае 2026 —
   сигнатура на VLESS+TCP+REALITY с настройками по умолчанию по размерам
   первых пакетов и паузам между ними. Признаки, которые называют: отпечаток
   TLS, число параллельных соединений, подсеть назначения, несовпадение SNI и
   IP. Конфигурации с Vision/паддингом, gRPC и XHTTP, по тем же источникам,
   работали дольше. [Хабр, Хакер, vc.ru, traysub]
4. **Вложенный TLS** (научная работа, проверено в сети провайдера на миллион
   пользователей). Рукопожатие внутреннего TLS узнаётся по размерам, паузам
   и направлениям пакетов даже под шифрованием, со случайным паддингом и
   несколькими слоями туннелей. Мультиплексирование частично помогает;
   «паддинг + мультиплекс» принципиально ограничены, потому что не убирают
   всплески и лишние круги запрос-ответ. [Xue и др., USENIX Security 2024]
5. **QUIC/UDP 443** (наблюдения). На многих провайдерах QUIC фильтруется по
   SNI из QUIC Initial или блокируется целиком; на UDP к зарубежным
   хостингам — отдельные ограничения. Транспорты на QUIC в России ненадёжны.
   [ntc.party, исследования 2024]
6. **ECH** (замерено). ClientHello с ECH и SNI `cloudflare-ech.com` к IP
   Cloudflare отбрасывается. ECH в России — не средство маскировки, а
   признак. [net4people #417]

## Обновление: что известно на ноябрь 2026

Повторный поиск дал ещё несколько механизмов. Уровень уверенности тот же:
замеры участников net4people надёжнее блогов.

7. **Лимит числа TLS-соединений к одному серверу** (замеры пользователей,
   ноябрь 2025 — 2026). У части домашних провайдеров (МТС/МГТС и др.)
   соединение глохнет, «как только через туннель пошли данные», тем раньше,
   чем больше трафика; через ~60 с можно подключиться снова; только на
   порту 443. Отдельный отчёт: ~12 TLS-соединений с SNI к одному серверу за
   короткое время — блок примерно на 120 с. Помогало: меньше TLS-соединений
   (mux), другой порт. [net4people #546, #603]
8. **Оценка ClientHello по подсети, SNI и отпечатку** (вторичный разбор,
   2026). Отпечатки Chrome, Safari и iOS к «подозрительным» подсетям
   хостингов задерживаются, Firefox, Android (OkHttp) и Edge проходят.
   Отдельно подтверждена блокировка по конкретному отпечатку для DTLS
   (Snowflake, с 30.03.2026): фильтр по JA3/JA4 — реальный инструмент.
   [avsisp, net4people #603]
9. **Массовые баны IP популярных VPS** (4 августа и 21 сентября 2026).
   Блокировались тысячи адресов у ряда хостингов, в том числе с одним
   AmneziaWG. Заметное наблюдение: у сервера с разными входящим и
   исходящим IP забанили только исходящий — тот, с которого ходили на
   российские сайты. [net4people #671]
10. **«Подключено, но трафик не идёт» / обрыв через 30–60 с** — так описывают
   поведенческие блокировки 2026 года; детали не подтверждены. Обнаружение
   TUN-режима на стороне DPI — не подтверждено (скорее DNS и всплеск
   соединений). [Хабр, anti-malware.ru, net4people #663]

**Что это значит для cypher и что сделано в 0.2.1:**

| Механизм | Как cypher себя ведёт |
|---|---|
| Лимит TLS-соединений (обычный режим) | **сильная сторона**: всё идёт по одному мультиплексированному соединению (у Xray без mux — соединение на каждое подключение приложения) |
| Лимит TLS-соединений (режим «против заморозки») | **противоречие**: короткие соединения как раз множат их число. Сделано: лимит 8 новых соединений за 10 с (настраивается), паузы при неудачах до 30 с, а `auto` выключает режим, если новые соединения перестают проходить |
| Оценка отпечатка | по умолчанию Firefox; добавлен Android (OkHttp); `random` выбирает только из Firefox, Edge и Android |
| Бан исходящего IP за российский трафик | клиент по умолчанию отправляет российское напрямую; на сервере — опция `CYPHER_BLOCK_RU=1`, запрет выхода на российские сайты |
| Только порт 443 | порт сервера настраивается (`CYPHER_LISTEN`/проброс в compose); но нестандартный порт сам по себе заметен — пробовать, если на 443 обрывы |

Цена режима «против заморозки» с лимитом соединений: ~6 КБ/с («Осторожно»,
8 соединений за 10 с), ~16 КБ/с («Быстрее», 20 за 10 с). Этого хватает
мессенджерам и лёгким страницам, но не загрузкам. Поэтому режим
включается сам только после обнаруженной заморозки.

## Разбор статей: схема ТСПУ июня 2026 и «всё о ТСПУ» (v0.2.2)

Прочитаны целиком: [«Пожалуй, всё, что надо знать о ТСПУ»](https://habr.com/ru/articles/1095490/),
[«Заморозка по fingerprint»](https://habr.com/ru/articles/1047442/) и
вложенные в них [«О схеме ограничений РКН в июне 2026-го»](https://habr.com/ru/articles/1044396/),
[«Как ТСПУ ловит VLESS в 2026»](https://habr.com/ru/articles/1009542/),
[«Как DPI вычисляет MTProto-прокси»](https://habr.com/ru/articles/1041486/),
[«Как починить блокировку сайта от ТСПУ»](https://habr.com/ru/articles/1045684/).
Сами авторы предупреждают, что пороги собраны по одному источнику
(наблюдения через dpi-ch) и это рабочие гипотезы, а не константы.

**Схема июня 2026 («сибирская»).** Цензор оценивает каждый ClientHello.
Ограничение срабатывает, только если выполнены все условия сразу:

1. IP сервера — в «подозрительной» подсети/AS (зарубежные и многие
   российские хостинги);
2. отпечаток подозрительный: Chrome, Safari, iOS (Firefox, Android OkHttp,
   Edge пока проходят);
3. к одному SNI начато больше 3 TLS-соединений почти одновременно
   (с разницей меньше ~350–400 мс; по другой версии — за 60 с).

Тогда все текущие и новые TLS-соединения к узлу «замерзают» на ~120 с
(TCP проходит, TLS — нет). Смена отпечатка во время заморозки — ещё 600 с
на все TLS к узлу (16.06 эту часть, по наблюдениям, убрали). Ретраи
продлевают заморозку: каждый новый залп хендшейков снова переполняет
счётчик. Состояние привязано к паре (IP клиента, SNI).

**Поведенческие признаки** (1095490, 1041486, 1009542): долгое соединение
с keepalive через *равные* промежутки (так вычисляют MTProto), симметричный
трафик и поток без пауз, однообразные размеры записей, ответ сервера до
запроса клиента, много клиентов с побайтно одинаковым ClientHello на один
IP, вложенный TLS. Обнаруженные IP попадают в списки.

**Что из этого было уязвимостью cypher и что исправлено:**

| Уязвимость | Было | Стало (v0.2.2) |
|---|---|---|
| Залп хендшейков | если туннеля нет, каждый ожидающий запрос открывал **своё** TLS-соединение: 10 запросов после обрыва = 10 параллельных хендшейков — ровно условие №3 | одновременно идёт не больше **одного** хендшейка, остальные запросы ждут его; между началами хендшейков ≥ 1 с и не больше 3 за минуту |
| Шторм ретраев | после обрыва или неудачи — сразу новая попытка, и так по кругу | после неудачи пауза 2 с, удваивается до 2 мин (±20 %); запросы в это время сразу получают ошибку, а не долбят сервер |
| Смена отпечатка | `random` выбирал новый браузер **для каждого соединения** — именно то, за что давали 600 с | `random` выбирает браузер один раз по ключу и серверу: у одного пользователя он не меняется никогда (и после перезапуска), а разные пользователи одного сервера выглядят как разные браузеры — против корреляции «все клиенты с одинаковым ClientHello» |
| Ровный keepalive | smux слал служебный кадр каждые 15 с ровно — «пульс» долгого соединения | интервал случайный, 10–40 с, и только пока есть открытые потоки; простаивающее соединение молчит, как простаивающий HTTP/2 |
| Пинг-«сердцебиение» | при открытом, но молчащем потоке (websocket, push) клиент пинговал сервер каждые ~4 с | пинг — только когда данные шли и вдруг прекратились, или когда наш запрос остался без ответа; молчащий поток проверяется один раз |
| Переход в «против заморозки» не по той причине | первая же заморозка включала короткие соединения — при «сибирской» схеме это худший ответ: много соединений | включается только после **второй** заморозки за 10 минут: она возможна, лишь если переподключение между ними удалось, то есть это лимит ~16 КБ на соединение, а не блок узла |
| Несколько соединений | при ротации старое соединение дорабатывает, пока открыто новое (кратко — два) | опция `singleConnection`: строго одно соединение (см. ниже) |

Что уже было в порядке: сервер никогда не пишет первым (HELLO — ответ на
запрос клиента), без ключа отвечает обычный сайт по HTTP/1.1 и HTTP/2,
отпечаток по умолчанию — Firefox, размеры начала каждого потока
рандомизированы.

**Что не исправить настройкой протокола:** подсеть хостинга (выбирайте
хостинг), асимметрия трафика (видео и загрузки похожи на веб, мессенджеры —
нет), долгий объём на один IP. Против этого — ретранслятор и транспорт
через CDN (п. 1 и 4 ниже).

### Одно соединение (`singleConnection`)

```json
{ "tag": "proxy", "type": "cypher", "server": "example.com:443", "key": "…",
  "singleConnection": true }
```

* к серверу всегда не больше одного TLS-соединения — ни при ротации, ни
  при обрыве, ни при всплеске запросов;
* ротация только «разрыв, потом новое»: соединение, отработавшее свой срок,
  закрывается, когда на нём не осталось потоков, а следующее открывается по
  первому запросу. Пока потоки есть — оно продолжает работать;
* простаивающее соединение закрывается через 1–3 мин (`rotation.idle`);
* режим «против заморозки» выключен: ему нужно новое соединение каждые 8 КБ.

Плюсы: ни одного параллельного хендшейка, поведение как у браузера с
HTTP/2 к одному сайту. Минусы: при постоянной нагрузке соединение живёт
долго и несёт большой объём (это тоже признак, хотя слабее залпа
хендшейков), и лимит ~16 КБ на соединение у мобильных операторов не
обходится — там нужен `antiFreeze`. В ссылке — `sc=1`
(`cypher link … -single`), в nevio — Настройки → Подключение → Соединения.

Обычный режим (по умолчанию) тоже держит одно соединение и открывает новые
по одному; отличие — во время ротации ненадолго живут два.

## Насколько уязвим cypher сейчас

| Метод | cypher сейчас | Почему |
|---|---|---|
| Сигнатура «настроек по умолчанию» | устойчивее Xray | размеры первых пакетов случайны, начало каждого потока нарезано |
| Активное зондирование | устойчив | без ключа — обычный сайт на nginx |
| Отпечаток TLS | устойчив | uTLS, настоящие браузерные профили; отпечаток не меняется между соединениями |
| Залп хендшейков / ретраи («сибирская» схема) | **устойчив** (с v0.2.2) | один хендшейк за раз, паузы после неудач, `singleConnection` |
| Несовпадение SNI и IP | устойчив | свой домен, SNI = IP = сертификат |
| **Заморозка ~16 КБ к хостингам** | **устойчив** (с v0.2) | заморозка распознаётся за секунды; режим «против заморозки» ведёт сессию короткими соединениями ниже порога |
| **Белый список IP (мобильные)** | **уязвим, как Xray** | сервер за границей не в списке |
| Вложенный TLS (ML-классификатор) | частично | паддинг и мультиплекс помогают, но не убирают всплески |
| Подсеть/ASN хостинга | уязвим, как Xray | зависит от выбора хостинга, не от протокола |
| Блокировка QUIC | не затрагивает | QUIC не используем |

## Что добавить

По приоритету — сначала то, что закрывает самые массовые сейчас методы.

| Мера | Статус |
|---|---|
| 1. Ретранслятор внутри страны | отложено; задел в протоколе (`CapRelay`) и в сервере (`Upstream`) |
| 2. Сессия поверх коротких соединений | **сделано в v0.2** (`antiFreeze`) |

### 1. Ретранслятор внутри страны (цепочка серверов) — главное

Клиент подключается к узлу cypher в российском облаке, тот передаёт
трафик зарубежному серверу. Для ТСПУ на мобильной сети это соединение с
российским облаком, а не с зарубежным хостингом: правило «заморозки после
16 КБ к Hetzner/OVH» не срабатывает, а IP российского облака чаще
оказывается в белом списке. Участок «облако → заграница» идёт между
дата-центрами, где фильтрация мягче.

Что сделать: режим `relay` в сервере (вход как у обычного сервера,
выход — `cypher` outbound к следующему серверу), ссылки с цепочкой узлов,
в nevio — выбор «через ретранслятор».

### 2. Сессия, не привязанная к TCP-соединению

Чтобы пережить «заморозку после N КБ», данные одной сессии должны
переходить между многими короткими соединениями без потерь: номера и
подтверждения кадров на уровне сессии, переотправка того, что застряло в
замороженном соединении, бюджет байт на соединение (например 12 КБ) с
заменой соединения до порога. Так устроены XHTTP (packet-up) и meek.
Плюс автоопределение: если соединение «замёрзло» (данные в пути, ответа
нет N секунд), клиент сам переходит в этот режим.

Цена — скорость и число соединений; поэтому только как режим, который
включается при обнаружении заморозки или вручную.

### 3. Форма трафика против классификатора вложенного TLS

Сейчас мы паддим и режем начало потоков. По выводам Xue и др. этого мало:
нужно сглаживать **всплески** и **круги запрос-ответ**. Что можно:

* склейка: ответ сервера на рукопожатие внутреннего TLS накапливается
  несколько миллисекунд и уходит одной пачкой, как отдаёт страницу
  веб-сервер;
* опережающий трафик: сервер отправляет заполнитель, пока клиент ждёт, чтобы
  паузы не повторяли круги внутреннего TLS;
* профили размеров записей по настоящему браузерному HTTP/2, а не
  равномерный случай.

### 4. Транспорт поверх обычного HTTP/2 (как XHTTP)

Поток как последовательность HTTP-запросов и ответов к сайту. Даёт
естественную форму «браузер грузит страницу», работает за любым
HTTP-прокси и балансировщиком и сочетается с пунктом 2.

### 5. Мелочи с хорошим соотношением цены и пользы

* **Проверка IP сервера при установке:** `install-server.sh` и Docker
  предупреждают, если IP в известных «заморожённых» диапазонах (Hetzner,
  DigitalOcean, OVH, Cloudflare), и советуют менее заметный хостинг.
* **Число соединений по умолчанию — 1** на мобильных сетях (число
  параллельных подключений называют признаком).
* **Не использовать ECH и QUIC** для внешнего слоя в России — прописать
  явно.
* **Порт 443 и только он**: нестандартные порты для TLS выглядят подозрительно.

### Чего делать не стоит

* Больше случайного паддинга: против классификаторов вложенного TLS он
  ограничен, а трафик растёт.
* Полностью случайный протокол без TLS: такие (Shadowsocks, obfs4) режутся
  эвристиками энтропии.
* Подмена SNI на чужой домен при своём IP: SNI и IP сверяются.
