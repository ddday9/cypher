# Протокол cypher, версия 1

Статус: черновик, реализован в этом репозитории.

## Цели

1. **Не выделяться для DPI.** Снаружи соединение — обычный HTTPS (TLS 1.3) к
   обычному сайту, с отпечатком ClientHello настоящего браузера.
2. **Не выдавать себя при активном зондировании.** Кто угодно, кроме клиента с
   ключом, получает настоящий сайт: браузер, сканер, цензор, повтор записанного
   трафика.
3. **Не изобретать криптографию.** Шифрование и аутентификацию сервера даёт
   TLS 1.3; протокол добавляет только аутентификацию клиента (HMAC-SHA256) и
   маскировку размеров.

## Модель угроз

| Противник умеет | Защита |
|---|---|
| Видеть весь трафик, SNI, IP, размеры, тайминги | Настоящий TLS к своему домену; паддинг; мультиплекс |
| Проверять отпечаток ClientHello (JA3/JA4) | uTLS: ClientHello Chrome/Firefox/Safari |
| Подключаться к серверу самому (active probing) | Без валидного токена — настоящий сайт (HTTP/1.1 и HTTP/2) |
| Повторять записанные данные | Метка времени ±120 с и кэш nonce |
| Подменять сертификат (MITM) | Клиент проверяет сертификат обычным образом |

Не защищает (пока): от блокировки по IP/ASN, от анализа объёма трафика на один
IP за долгое время, от статистики «одно долгое соединение». См. «Дальнейшие
этапы».

## Схема

```
TCP → TLS 1.3 (настоящий сертификат домена, ALPN h2/http1.1)
        └─ первые байты от клиента:
             валидный auth-заголовок → слой записей → smux → потоки
             что-то другое           → встроенный HTTP/1.1 / HTTP/2 сайт
```

## 1. Транспорт

* Сервер слушает TCP 443, сертификат — настоящий, на собственный домен
  (Let's Encrypt; сервер может получать его сам через ACME TLS-ALPN-01). SNI, IP, сертификат и сайт согласованы («self-steal»).
* Сервер предлагает ALPN `h2`, `http/1.1` — как обычный веб-сервер.
* Клиент строит ClientHello через uTLS (по умолчанию Firefox) и проверяет
  сертификат сервера.

## 2. Аутентификация клиента

Первые байты внутри TLS от клиента:

```
+--------+-----------+--------+--------+------------+
| nonce  | timestamp | padLen | mac    | padding    |
| 16 B   | 8 B (BE)  | 2 B BE | 32 B   | padLen B   |
+--------+-----------+--------+--------+------------+
mac = HMAC-SHA256(key, "cypher/v1/auth" || nonce || timestamp || padLen)
```

* `key` — 32 случайных байта на пользователя (`cypher genkey`), в конфиге в
  base64url.
* `timestamp` — Unix-время в секундах; сервер принимает расхождение до ±120 с.
* `nonce` — случайный; сервер помнит nonce за последние ~4 минуты и отвергает
  повторы.
* Первый байт `nonce` никогда не бывает `A`–`Z`. Любой HTTP-запрос (`GET`,
  `POST`, …, и преамбула HTTP/2 `PRI * HTTP/2.0`) начинается с заглавной
  латинской буквы, поэтому сервер узнаёт браузер по первому же байту и сразу
  отдаёт ему сайт, не дожидаясь 58 байт.
* `padding` — 0–768 случайных байт, чтобы первая запись не имела постоянного
  размера.
* Заголовок отправляется в одной записи TLS вместе с первым кадром данных.

Сервер перебирает ключи пользователей и сравнивает MAC за постоянное время.

**Если проверка не прошла** (неизвестный ключ, просроченная метка, повтор,
HTTP-запрос, EOF) — все уже прочитанные байты передаются встроенному
веб-серверу, как будто он читал их сам. Ответ неотличим от обычного сайта:
`200` на `/`, `404` на остальное, или ваш сайт (`fallback.dir` /
`fallback.proxy`).

## 3. Слой записей (паддинг)

После аутентификации обе стороны обмениваются записями:

```
+---------+--------+--------+----------+
| dataLen | padLen | data   | padding  |
| 2 B BE  | 2 B BE |        | (нули)   |
+---------+--------+--------+----------+
dataLen + padLen ≤ 16380   (запись + заголовок помещаются в одну TLS-запись)
```

Запись — это просто кусок байтового потока: границы записей не несут смысла,
поэтому отправитель может резать данные где угодно, а получатель склеивает
их обратно.

Политика нарезки и паддинга:

* **«Формируемые» записи** — первые 16 записей соединения и первые 8 кадров
  данных *каждого* потока smux (отправитель видит заголовок кадра smux и
  отслеживает поток по его id). Именно там проходит рукопожатие внутреннего
  TLS (ClientHello, ServerHello, сертификаты), по которому узнают TLS-in-TLS.
  Такие данные режутся на куски случайного размера 200–4096 байт, к каждому —
  случайный паддинг 0–512 байт. Так у каждого нового потока, а не только у
  первого, исчезает узнаваемая последовательность размеров.
* **Остальные записи** — до 16380 байт без паддинга; мелкие записи
  (< 256 байт: keepalive, служебные кадры) получают паддинг 0–256 байт.

Паддинг передаётся внутри TLS, поэтому его содержимое (нули) не видно; меняются
только видимые размеры TLS-записей.

## 4. Мультиплексирование

Поверх записей работает [smux](https://github.com/xtaci/smux) v2: много
пользовательских соединений в одном TLS-соединении, с управлением потоком на
каждый поток. Так ни одно пользовательское соединение не порождает отдельное
TLS-рукопожатие к серверу (которое было бы видно).

## 4a. Пул соединений и ротация (клиент)

Одно вечное толстое соединение к одному IP — тоже признак. Поэтому клиент
держит небольшой пул TLS-соединений и меняет их, как это делает браузер:

* до `connections` (по умолчанию 1) соединений параллельно; новый поток идёт
  в наименее загруженное, пул добирается в фоне;
* у каждого соединения свой случайный срок жизни (по умолчанию 5–20 минут) и
  свой лимит трафика (64–512 МБ). Когда он исчерпан, соединение больше не
  получает новых потоков и закрывается, как только допишут текущие (но не
  позже чем через час);
* соединение без потоков дольше случайного времени простоя (1–3 минуты)
  закрывается совсем — в простое к серверу ничего не висит.

Все пределы — диапазоны, каждое соединение выбирает своё значение, поэтому
нет фиксированного периода, по которому можно было бы опознать клиента.

Темп хендшейков (против «сибирской» схемы ТСПУ: >3 почти одновременных
TLS-хендшейков к одному SNI → заморозка узла на ~120 с):

* одновременно идёт не больше одного хендшейка; запросы, которым нужно
  соединение, ждут его, а не открывают свои;
* между началами хендшейков не меньше 1 с, и не больше 3 за 60 с;
* после неудачи — пауза 2 с, удваивается до 2 мин (±20 %); запросы в это
  время сразу получают ошибку;
* отпечаток ClientHello у outbound один и тот же для всех соединений
  (`random` выбирается по хэшу ключа и сервера).

`singleConnection: true` — строго одно соединение: отработавшее срок
закрывается, только когда на нём нет потоков, следующее открывается по
запросу; режим «против заморозки» выключен.

## 4b. Keepalive

Встроенный keepalive smux (кадр каждые 15 с ровно) выключен: ровный пульс
долгого соединения — известный признак туннеля. Вместо него обе стороны
шлют такой же кадр smux NOP через случайные 10–40 с, и только пока открыты
потоки. Соединение без потоков молчит. Старые версии (до 0.2.2) закрывают
сессию после 60 с без данных, поэтому им keepalive шлётся всегда; новые
версии сообщают о себе флагом `QuietIdle` (клиент) и возможностью
`QuietIdle` в HELLO (сервер).

Кто ничего не получил от пира 2 мин при открытых потоках (5 мин без
потоков — сервер), закрывает соединение.

Проверка заморозки (PING/PONG, протокол 2) срабатывает, когда данные шли и
перестали дольше чем на 3 с, или когда отправленное осталось без ответа;
молчащий открытый поток проверяется один раз, а не каждые несколько секунд.

## 5. Запрос потока

Клиент открывает поток и пишет:

```
+-----+-----+------+----------------------+--------+
| ver | cmd | atyp | addr                 | port   |
| 1   | 1   | 1    | 4 / 16 / 1+len байт  | 2 B BE |
+-----+-----+------+----------------------+--------+
ver = 1; cmd: 1 = TCP, 3 = UDP; atyp: 1 = IPv4, 3 = домен, 4 = IPv6
```

Сервер отвечает одним байтом статуса и, если `0`, дальше идут данные:

| Код | Значение |
|---|---|
| 0 | OK |
| 1 | Общая ошибка |
| 2 | Запрещено (приватный адрес) |
| 4 | Узел недоступен / не резолвится |
| 5 | Соединение отклонено |
| 6 | Дальше идёт сквозное шифрование с выходом (раздел 8) |

### UDP (cmd = 3)

После статуса `0` поток несёт датаграммы. Каждая кодируется так:

```
+------+----------------------+--------+---------+---------+
| atyp | addr                 | port   | length  | payload |
| 1    | 4 / 16 / 1+len байт  | 2 B BE | 2 B BE  |         |
+------+----------------------+--------+---------+---------+
```

От клиента адрес — получатель, от сервера — отправитель ответа. Один поток
может слать пакеты разным адресатам (DNS, QUIC, игры). Сервер открывает для
потока один UDP-сокет и закрывает его после 2 минут без пакетов. Клиент
маршрутизирует каждый пакет отдельно (правила с `network: udp`), так что
одна SOCKS5-ассоциация может идти частью в туннель, частью напрямую.

Сервер сам резолвит домены и по умолчанию не подключается к loopback, частным,
link-local, CGNAT и multicast-адресам (`allowPrivate: false`) — даже если домен
указывает на 127.0.0.1.

## 6. Версия 2 и совместимость

Версия 2 согласуется так, что версия 1 ничего не замечает:

* **Клиент → сервер:** расширение внутри паддинга аутентификации (сервер
  версии 1 паддинг читает и отбрасывает):

  ```
  magic "CY2\x01" | flags (2) | session (16) | seq (4) | mac (16)
  mac = HMAC-SHA256(key, "cypher/v2/ext" | nonce аутентификации | первые 26 байт)[:16]
  ```

  Флаги: `V2` (понимаю служебные записи), `Segmented` (это соединение
  несёт сессию «против заморозки»), `Attach` (присоединиться к сессии
  `session` как соединение номер `seq`), `QuietIdle` (не закрываю сессию
  без потоков из-за тишины, см. 4b).
* **Служебные записи:** бит `0x8000` в поле `padLen` записи. Сервер шлёт их
  только клиентам, приславшим расширение, клиент — только серверу, который
  ответил `HELLO`.
* **HELLO** (сервер → клиент, в ответ на аутентификацию): версия и
  возможности — `Ping`, `Segmented`, `QuietIdle`, `Relay` (сервер —
  ретранслятор, раздел 8), `E2E` (сервер принимает сквозное шифрование).
* **PING/PONG:** клиент пингует туннель, который молчит дольше 3 секунд при
  открытых потоках; нет ответа за 4 секунды — туннель «заморожен» и сразу
  заменяется новым.

| Сервер | Клиент | Что происходит |
|---|---|---|
| v1 | v1 | как раньше |
| v1 | v2 | расширение отброшено сервером; обычный туннель (режим «против заморозки» распознаётся как неподдерживаемый за 3 с и больше не пробуется) |
| v2 | v1 | сервер не видит расширения и не шлёт служебных записей — как раньше |
| v2 | v2 | HELLO, PING/PONG, режим «против заморозки» |

## 7. Режим «против заморозки» (сессия поверх коротких соединений)

ТСПУ на мобильных сетях замораживает TCP-соединение с зарубежным хостингом
после ~16 КБ. Сессия этого режима не привязана к соединению:

* поверх сессии работает тот же smux; сессия — надёжный поток байт,
  который переносят соединения-«носители» по очереди;
* данные идут записями `DATA` (смещение, флаг «есть ещё», данные),
  получатель подтверждает их `ACK` (накопительное смещение);
* каждая сторона отправляет по одному носителю не больше бюджета
  (по умолчанию 8 КБ вместе с накладными), затем шлёт `DRAIN`; клиент
  заранее (на ¾ бюджета) открывает следующий носитель с флагом `Attach`;
* при переходе на новый носитель всё неподтверждённое отправляется заново;
  сервер не подключает носитель с номером меньше текущего;
* заморозка до исчерпания бюджета распознаётся по флагу «есть ещё» без
  данных 1,5 с или по отсутствию ACK 2 с — клиент открывает новый носитель;
* сервер закрывает сессию, у которой нет носителя 2 минуты.

Режимы клиента (`antiFreeze`): `auto` — обычные туннели; если заморозка
повторилась в течение 10 минут (значит, новое соединение между ними
прошло, и это лимит на соединение, а не блок узла), 30 минут короткие
соединения; `on` — всегда; `off` — никогда.
Цена — скорость (каждые 8 КБ — новое TLS-соединение), поэтому `auto` по
умолчанию. Новые соединения ограничены (`antiFreezeRate`, по умолчанию 8 за
10 с): некоторые провайдеры блокируют сервер за ~12 быстрых TLS-соединений.
При неудачных подключениях — паузы до 30 с; `auto` выходит из режима, если
новые соединения перестают проходить.

## 8. Ретранслятор и сквозное шифрование

Ретранслятор — обычный сервер cypher с `upstream`: для своих клиентов он
сервер, для выхода — клиент (одно общее соединение, пул из раздела 4a).
Каждый запрос он маршрутизирует (`direct` / `exit` / `block`, правила как у
клиента, `inboundTag` = имя пользователя). Подробно — [relay.md](relay.md).

**Сквозное шифрование.** Клиент, у которого в ссылке есть ключ
пользователя на выходе (`ek`) и публичный ключ выхода (`epk`), и сервер
которого объявил `Relay`, пишет в поток:

```
ver=1 | cmd | 0x80 | atyp | addr | port | frame(Noise msg1)
frame = len (2 B BE) | данные
```

* ретранслятор по адресу решает маршрут. `direct`/`block` — он
  пропускает frame и отвечает как на обычный запрос (статус и данные в
  открытом виде, внутри внешнего TLS). `exit` — открывает на соединении с
  выходом поток `ver=1 | cmd=4 (E2E)` и дальше только копирует байты;
* выход отвечает статусом 6 и frame(Noise msg2). Дальше — frames, в
  каждом `dataLen (2 B) | data | паддинг` (мелкие — до 256 байт паддинга);
* рукопожатие — **Noise_NK_25519_ChaChaPoly_BLAKE2s**, пролог
  `cypher/v1/e2e`. В msg1 — обычный заголовок аутентификации (раздел 2) с
  ключом `ek` и запрос (раздел 5): выход проверяет пользователя, метку
  времени и повтор nonce так же, как у прямого клиента, и применяет его
  правила. В msg2 — статус запроса;
* с `hd=1` клиент шлёт `ver=1 | cmd=4` без адреса: ретранслятор не
  маршрутизирует и сразу передаёт поток выходу;
* если выход не объявил `E2E` (старая версия), ретранслятор обслуживает
  запрос как обычный: пропускает frame и отвечает статусом 0 — клиент
  продолжает в открытом виде (внутри TLS до ретранслятора).

Клиент сразу после подключения к ретранслятору отправляет заголовок
аутентификации отдельно (пустой записью), чтобы получить HELLO до первого
запроса.
